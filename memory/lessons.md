## 2026-06-07 — bc-chime (OUTCOME: flashpaper.chime.com ACCEPTED AS VALID, marked DUPLICATE of a 2021 report)
**Proposal**: out-of-band operator review (outcome ingest)
**Applied rules**: rule-endpoint_hunter-long_exposure_duplicate_prior-5e7c2 (NEW, medium, SOFT)

The flashpaper.chime.com report (Bugcrowd, submitted 2026-05-22 as P2/High active) was marked **Duplicate** by brunoc_bugcrowd on 2026-05-27 — duplicate of a *"File Upload Bug in flashpaper..."* report submitted **2021-10-30** — but explicitly **accepted as a valid issue**, state Unresolved, with duplicate points to accrue if the P2 original reaches a final state. This is the fourth disposition ingested and the FIRST that was technically accepted rather than rejected.

This one matters because it's the control case: it shows the pipeline CAN produce a correct, well-formed finding. Ownership was genuine — flashpaper.chime.com is a real host under the declared `*.chime.com` Primary-Target wildcard, not the airtable-style name-derivation guess. The core claim (unauthenticated public deployment of an internal-only secret-sharing tool) was accurate and accepted. The impact section did carry some conditional speculation ("IF that secret contained a credential...") but the headline finding stood on its own. Endpoint-hunter is, on the disposition evidence so far, the pipeline's best-performing engine.

The only learning is duplicate-risk, and it's a soft one: the service had 3+ years of Wayback/archive indexing (earliest snapshot 2022-08-03) and the duplicate's original predated our submission by 4.5 years. A multi-year publicly-archived exposure on a prominent brand domain has a near-certain prior-report probability. This is the same long-exposure-duration duplicate signal as elastic's 12-year secret, generalized to exposed services. But unlike the secret cases, the right response is NOT to suppress — the finding was valid and may still earn points, and private reports are invisible so duplicate-risk is partly unavoidable. Added `rule-endpoint_hunter-long_exposure_duplicate_prior-5e7c2` as a SOFT annotation: flag high duplicate-risk and surface to the operator to calibrate effort/expectation, but still draft.

Disposition tally now 4-of-6, and the shape is clearer with the control case in hand: the three REJECTIONS (airtable N/A, TFH + elastic duplicate-low-impact) all share the "positive-looking signal treated as the finding" failure; the one ACCEPTANCE (chime) had genuine ownership and a real, non-inferred finding. The discriminator between a valid finding and a rejected one in this dataset is exactly the two judgments the loop was weakest at — real ownership, and impact argued from evidence rather than from a verification/derivation signal.

## 2026-06-07 — elastic (OUTCOME: H1 #3739639 closed DUPLICATE of #2926439; original closed INFORMATIVE / no impact)
**Proposal**: out-of-band operator review (outcome ingest)
**Applied rules**: rule-secret_hunter-history_only_test_fixture_low_impact-9d2e1 (NEW, high)

The SauceLabs-credential report (H1 #3739639, submitted 2026-05-16) was closed **Duplicate of #2926439** by h1_analyst_sanji on 2026-05-18. The original was closed **Informative**: *"the credential has no impact. The account was associated with a former employee and cannot access any program data."* Third platform disposition ingested, third negative.

The severity discipline actually worked here — the report was correctly capped high→low against the `elastic.co credentials` asset cap. The failure was that it should not have been drafted at all, and three independent discount signals were present and ignored: (1) the secret lived in a **test-fixture path** — `test/utils/keys.js` — a CI/test credential by location; (2) it was **git-history-only** (deleted from HEAD); (3) it was **~12 years old** in a flagship public repo (`elasticsearch-js`). Any one of those should lower expected value; all three together make it a near-certain duplicate of an orphaned, no-access account. What overrode all three was `trufflehog Verified=true` — the same false inference as toolsforhumanity. Verified proves the *issuer* accepts the key; it says nothing about whether the account can touch program data. Here it couldn't (former employee). The impact section was again speculative — "past test runs MAY have recorded sensitive data," "Sauce Connect pivot IF configured" — the inflation pattern the toolsforhumanity disposition already flagged.

This is precisely the pattern the dynatrace engagement (2026-05-30) later articulated as a non-finding — "history-only secret needing active (likely third-party) infra access to PoC" — and deliberately did NOT draft. But dynatrace produced a narrative lesson, not a machine rule, so nothing retroactively protected the earlier elastic draft. Added `rule-secret_hunter-history_only_test_fixture_low_impact-9d2e1` (confidence=high) to enforce it: test-fixture path OR history-only OR very-old-in-popular-repo → default low-impact, route to manual triage, and Verified=true does NOT override the discount. If a PoC would require active access to third-party infra (Sauce Labs, RPC provider, SaaS dashboard), issuer-side verification does not satisfy impact.

Three-for-three negative dispositions, all the same shape: a positive-looking signal (name-derivation / trufflehog-verified) treated as the finding. The two secret-related ones (TFH, elastic) collapse to one rule of thumb — **verified-live is a precondition for a finding, never the finding itself; impact and freshness/context must be argued separately, and test-fixture/history-only/old-orphaned credentials usually fail that bar.**

## 2026-06-07 — toolsforhumanity (OUTCOME: H1 #3742794 closed DUPLICATE + program-assessed low-impact)
**Proposal**: out-of-band operator review (outcome ingest)
**Applied rules**: rule-report_drafter-blockchain_rpc_key_severity_cap-7c4d9 (NEW, high), rule-report_drafter-no_speculative_impact_inflation-3f2a8 (NEW, high)

The worldcoin Alchemy+Infura RPC-key report (H1 #3742794, submitted 2026-05-17) was closed **Duplicate of #3020852** by h1_analyst_anya on 2026-05-19 — the second platform disposition the loop has ingested, and like airtable's, negative. The triager helpfully surfaced the program's underlying per-credential assessment: the Alchemy key was *"just for testing services" without significant security impact* (#3020852); the Infura key was *"on a free plan and no longer being used by our simulator"* (#3543111). Both keys were trufflehog-verified-live, and both were low/no-impact.

The headline lesson is not the duplicate (we can't dedupe against others' private reports). It is that **trufflehog Verified=true proves only that the issuer accepts the credential — not that the credential has security impact.** The report leaned its entire severity argument on "verified active / never rotated → probably production," and inflated it further with speculative capabilities ('request interception', 'World ID proof interception', 'higher-privilege methods MAY also be available') that blockchain JSON-RPC keys simply do not grant. A triager who knew the keys were test/free-tier dismissed the whole thing. The "bundled framing insulates the primary finding from partial dismissal" tactic from the original entry provided no protection — the report went Duplicate as a unit.

This is a class lesson, not a one-off: blockchain RPC provider keys (Alchemy/Infura/QuickNode/Ankr/Moralis/etc.) are frequently public-by-design (client-side dApp project IDs), free-tier, or test/e2e fixtures, and grant at most rate-limit consumption against public chains. The loop has surfaced this exact class repeatedly — chainlink (15 verified Infura/Alchemy keys, correctly 0-reported) and okg (Infura/OKLink) — and now has ground truth that even an in-scope, owned, verified-live instance is low-value. Two rules added at confidence=high (triager-grounded, above the self-judged medium ceiling): (1) blockchain_rpc_key_severity_cap — default these informational, cap at low, route to manual triage, never auto-draft High unless non-public + non-free-tier + demonstrably-elevated-capability all hold; (2) no_speculative_impact_inflation — strip "MAY also be available"/"could potentially"/"request interception"-style claims; describe only observed capability.

Meta-pattern now visible across both ingested dispositions: the airtable N/A and this Duplicate are the same failure shape — a *signal that looks positive* (name-derivation; trufflehog-verified) was treated as *the finding itself*. Ownership-of-the-asset and impact-of-the-secret are the two judgments the loop is weakest at, and both only got corrected once a triager pushed back. Reinforces the #1 process recommendation: platform dispositions must feed the learning loop as a first-class signal.

## 2026-06-07 — airtable (OUTCOME: H1 #3766855 closed NOT APPLICABLE — first triager-grounded rule reversal)
**Proposal**: out-of-band operator review (outcome ingest, not a /retro proposal file)
**Applied rules**: rule-ownership_verifier-in_scope_bucket_derivation_override-951ed (REVOKED/disabled), rule-ownership_verifier-bucket_ownership_positive_proof_required-0a1b2 (NEW, confidence=high)

The api-staging-uploads listable-bucket report (H1 #3766855, drafted 2026-05-28) was closed **Not Applicable** by triager matthew_bryant on 2026-06-01: *"I see no evidence that Airtable owns this bucket."* This is the first real platform disposition the loop has ever ingested — every prior submission sits at platform_outcome=null — and it is a refutation of a finding the loop was confident enough about to spawn a discovery rule from.

The report shipped on `ownership_verdict_effective: owned_human_override` of an automated `unknown`. The override, and the discovery rule it spawned (951ed), both treated three signals as sufficient ownership provenance: (1) the bucket name strict-derives from in-scope `api-staging.airtable.com`, (2) a third-party GitHub repo's `staging.env` referenced the bucket, (3) the content was brand-plausible UUID PNGs. All three are squatter-compatible. S3 bucket names are a globally-unique first-come-first-served namespace; derivation proves nothing, a third-party repo referencing a bucket proves nothing about ownership, and brand-plausible content is not proprietary content. No CNAME chain from an in-scope host to the bucket and no first-party reference were ever established. A bucket-takeover specialist saw straight through it.

Critically, the flutteruki content-gate (44212/82369) added 10 days *later* would NOT have caught this. That gate is a negative filter: off-brand content (sbgcdn's Turkish cosmetics) → unowned. api-staging-uploads held brand-plausible content, so the content gate would have passed it. The two near-misses (sbgcdn FP caught, api-staging-uploads FP shipped) are the same root cause — domain/name ownership ≠ bucket ownership — but require complementary fixes: a negative content filter AND a positive-proof requirement.

Actions taken in this review: (1) recorded the disposition in memory/submissions/airtable.json platform_outcome with the triager's verbatim reason; (2) disabled rule 951ed (kept as a cautionary record, not deleted) with full disabled_reason provenance — the loop's first ground-truth-driven revocation; (3) added rule-ownership_verifier-bucket_ownership_positive_proof_required-0a1b2 at confidence=high (above the self-judged medium ceiling, because it's grounded in a triager verdict rather than self-judgment) requiring at least one positive ownership proof — verified CNAME chain, first-party repo reference, explicit scope listing, or uniquely-proprietary content — before any bucket reaches `owned`, else verdict=unknown and /draft-report refuses. Meta-lesson for the loop itself: the learning signal must include platform dispositions, not just pre-submission self-judgment — this single N/A reversed a rule that a month of clean-neg self-judgment had reinforced.

## 2026-06-07 — flutteruki
**Proposal**: `memory/lessons/proposals/20260607-151127-flutteruki.json`
**Applied rules**: rule-ownership_verifier-bucket_content_required-44212, rule-ownership_verifier-content_overrides_domain_signals-82369, rule-bucket_hunter-basename_skip-aa886

Flutter UK&I (flutteruki, H1) — bucket hunt (80 candidates, Pass A only, mass_scanning_allowed=false cap), takeover hunt (483 enumerated, 100 strict cap, 4 CNAME, 0 vulnerable), secrets not run (no source_code scope signal). Net: 0 reportable findings, but the engagement produced the most important near-miss false-positive the pipeline has seen to date.

The headline event was a near-miss false-positive on bucket 'sbgcdn' (eu-central-1). The acl_recheck gate correctly confirmed it publicly listable (24th s3scanner ACL-FP corroboration among the other 9 — all returned AccessDenied). The ownership-verifier then concluded 'owned' via three converging signals: in_scope_bucket_derivation_override-951ed fired (sbgcdn matches wildcard stem *.sbgcdn.com), wildcard_stem_dns_override-a18c1 fired (sbgcdn.com is MarkMonitor+Cloudflare-registered, program-controlled DNS), and the standard 2-of-3 aggregation read A=ambiguous/B=positive/C=positive — all three confirming the DOMAIN sbgcdn.com is Flutter/SBG-owned. The rules are correct about the domain. They were wrong about the bucket. Manual content inspection (aws s3api list-objects-v2 --no-sign-request, then aws s3 ls --recursive) revealed 55,743 objects / 8.5GB of Turkish-language beauty/cosmetics CMS content: img/yazi/st/yuz-maskesi.jpg (face mask), zerdecal-maskesi (turmeric mask), sac.mp4 (hair), generic Roboto/7-stroke admin-theme fonts — categorically unrelated to UK gambling brands. The verdict was manually corrected owned→unowned in the cache (c22ca9a121b7e9f2.json). The bucket was NOT reported.

The root cause is a structural blind spot in the ownership-verifier design: all three signal paths (GH code search, Wayback, DNS chain) reason about domain ownership, not bucket ownership. S3 bucket names are globally unique first-come-first-served; an unrelated Turkish beauty site registered 'sbgcdn' before Flutter did (or Flutter changed backing stores and abandoned the name). The domain sbgcdn.com pointing to Cloudflare's anycast serves SBG fonts via bet.sbgcdn.com, but the dns_chain.cname was null — bet.sbgcdn.com was NEVER confirmed to CNAME to sbgcdn.s3.amazonaws.com. The s3_bucket_resolves:true flag in the cache is non-probative: every existing S3 bucket resolves via virtual-hosting regardless of ownership. The wildcard_stem_dns_override and in_scope_bucket_derivation_override rules are necessary-but-not-sufficient conditions for bucket ownership. Had a report been drafted from the 'owned' verdict the rules fully supported, a false-positive would have shipped to H1.

The fix is a mandatory bucket content check gate inside the ownership-verifier, applied whenever a bucket is verified-listable (acl_recheck.verified_listable == true). The content check should be run before any ownership verdict is promoted to 'owned' for bucket assets, and a content classification that is categorically unrelated to the program's brand/domain/industry must override all prior domain-based signals and set the verdict to 'unowned'. This gate is the bucket-ownership analogue of the existing acl_recheck gate for listing claims — both intercept a signal that looks positive at the name/fingerprint level but is non-probative at the content level.

Takeover surface: 219 betfair.com and 133 paddypower.com subdomains were truncated by the 100-subdomain strict cap (mass_scanning_allowed=false). The skybet.com amass process was killed at 6 minutes with no output. crt.sh returned HTTP 502 on all three seed queries. The 4 CNAME subdomains found were all correctly classified as non-candidates (O365 autodiscover, same-zone internal, OOS parent, Cloudflare PA CDN). If revisiting, consider relaxing the cap or running a separate targeted takeover pass on betfair.com and paddypower.com specifically — each has hundreds of subdomains that deserve CNAME enumeration. Nuclei takeover pass was correctly skipped per automated_tools_allowed=false gate.
