## 2026-05-21 — wordpress
**Proposal**: `memory/lessons/proposals/20260521-134714-wordpress.json`
**Applied rules**: rule-secret_hunter-detector_ignore-9c696, rule-bucket_hunter-basename_skip-921e2, rule-bucket_hunter-basename_skip-9647b, rule-bucket_hunter-basename_skip-e8c52

WordPress engagement (2026-05-21): passive recon against the WordPress HackerOne program covering Pass A/B/C for secrets and Pass A for buckets. 80 bucket candidates generated from 13 domain-derived base names; 44 flagged by s3scanner; 0 verified listable after mandatory aws s3api recheck (44/44 AccessDenied, 100% s3scanner FP rate — fifth consecutive engagement with this outcome). 7 noseyparker candidates from 3 repo clones (WordPress/wordcamp.org, WordPress/wordpress.org, strangerstudios/paid-memberships-pro); 0 trufflehog-verified; 0 reports drafted.

What worked: the mandatory s3scanner ACL recheck gate (rule-bucket_hunter-s3scanner_acl_recheck_required-37651) prevented a wasted ownership-verifier queue — none of the 44 flagged buckets would have passed an ownership check anyway, given the program's explicit policy disclaimer that all wordpress-* S3 buckets are third-party. The rule fired exactly as intended and saved significant compute. noseyparker's 7 candidates were correctly identified as dismissible before any trufflehog verification was attempted: 5 intentionally-public Google Maps API keys (files literally named config-public.php and active-groups-map/index.html), and 2 Stripe SDK test fixture keys in PHPUnit setUp() calls.

What didn't work: Pass A trufflehog exited after scanning only ~18 of ~200 WordPress org repos. The existing passA_timeout_floor_secs rule (rule-secret_hunter-passA_timeout_floor_secs-d3ea2) sets its floor condition at 'orgs with >200 enumerated repos' — WordPress sits at exactly 200, just touching but not exceeding the threshold. The ~18/200 exit rate (9%) is far below what the timeout floor was designed to prevent; a future tweak should lower the threshold to >=150 repos or express it as 'repo_count >= 150' to catch orgs like WordPress. This is a narrative note only (H3 heuristic), not a hard rule, since re-parameterizing an existing scalar requires /forget.

What surprised us: the 'wordcamp' and 'buddypress' stems both produced bucket candidates (wordcamp, buddypress, buddypress-cdn) that are structurally just as unresolvable as the bare 'wordpress' stem — yet no basename_skip rule exists for any of them. The program policy wording covers all three stems equally ('third-party S3 buckets or droplets with WordPress in the name'). All three stems appear in scope as brand sub-projects that do not operate their own S3 infrastructure. Adding basename_skip for these three stems eliminates a meaningless ownership-verifier queue on every future wordpress engagement revisit.

Recommended pre-flight for next wordpress revisit: skip bucket hunting entirely unless the program's out_of_scope notice changes. If secrets are retried, ensure Pass A budget covers at least 150 repos (consider bumping passA_timeout_floor_secs threshold). Pass B/C on WordPress/wordpress.org and WordPress/wordcamp.org are the only repos that produced candidates — future runs can clone those two directly and skip Pass A's trufflehog org scan. strangerstudios/paid-memberships-pro is a third-party vendor repo; ownership must be verified against the WordPress program scope before any report is drafted.

## 2026-05-17 — bc-opera
**Proposal**: `memory/lessons/proposals/20260517-164542-bc-opera.json`
**Applied rules**: rule-secret_hunter-gh_org_supplement-f0e66, rule-bucket_hunter-s3scanner_acl_recheck_required-37651

Engagement against Opera Public Bug Bounty (bc-opera, Bugcrowd, max $5,000 across all severities): secret-hunter ran Pass A only (strict caps: automated_tools_allowed=false AND mass_scanning_allowed=false), scanning the `github.com/opera` org (3 public repos — terago, resources, logpeck-kibana-plugin). Trufflehog returned 0 verified secrets in 3 seconds; Pass B code searches for `opera`, `rtbscale`, and `savi` produced 60 entirely unrelated results (the token `opera` is too generic, `rtbscale`/`savi` matched tracker-radar lists and GNOME project files). 0 repos cloned; Pass C not run. Bucket-hunter scanned 80 candidates (mass_scanning_allowed=false cap), found 8 existing buckets across opera and osp basenames, all showing s3scanner `perm_all_users_read=ALLOWED`. Manual recheck with `aws s3api list-objects-v2 --no-sign-request` on all 8 confirmed AccessDenied — a clean sweep false-positive. No ownership-verifier runs (all 8 buckets were disqualified before that stage). No reports drafted. Engagement closed clean-negative.

What worked: the bucket-hunter cap behavior (mass_scanning_allowed=false capping at 80 candidates and skipping Pass B cloud_enum since Pass A found 8 hits) was correct and prevented over-enumeration. The `notes` field in the secrets output already flagged the `github.com/operasoftware` alternative org, so the gap was self-documented at scan time. The `memory` note about s3scanner ACL flags lying (from the Snapchat engagement) was referenced in the bucket JSON, which is exactly the right place for it — the operator caught it before drafting anything.

What did not work: Pass A landed on `github.com/opera` — a 3-repo personal-style org — because the dominant wildcard stem is `opera` and the 1-org strict cap forced exactly one guess. The canonical Opera Software GitHub org is `github.com/operasoftware` (50+ repos including browser engine components, core mobile app code, and internal tooling). This is almost certainly where leaked credentials would live. The stem-plus-suffix naming pattern (`operasoftware` vs `opera`) is not unique to Opera: `auth0` (Okta), `tmobile`, `atlassian-labs`, `grafana-labs` all follow the same form. The current heuristic has no fallback for this case under strict caps, creating a structural false-negative risk.

What surprised us: the s3scanner ACL false-positive rate was 8/8 — a complete sweep, not a partial miss. The Snapchat engagement had 1 such false positive (sc-core), which could have been dismissed as a one-off. Opera shows the same pattern at scale across 8 different bucket names in 4 different AWS regions (us-east-1, us-east-2, eu-central-1, ap-northeast-1, ap-south-1). This is strong corroboration that s3scanner `perm_all_users_read=ALLOWED` is a near-worthless signal when `objects_enumerated=false`. The recheck is not a belt-and-suspenders nicety — it is the gate.

Recommended pre-flight if bc-opera is revisited: (1) Run Pass A against `github.com/operasoftware` as the primary org (not `opera`) — the current `gh_org_override` mechanism supports this exactly. (2) The 8 buckets confirmed existing but AccessDenied can be passed directly to ownership-verifier if there is ever a policy relaxation that allows listing. (3) Pass B code searches for `opera` as a keyword are structurally unproductive — too generic. Consider adding `operasoftware` and `opera-gx` as more specific search tokens for any future Pass B run. (4) s3scanner recheck must be applied before ownership-verifier is invoked on any bucket showing `all_users_read=ALLOWED` with `objects_enumerated=false`.

## 2026-05-16 — automattic
**Proposal**: `memory/lessons/proposals/20260516-191601-automattic.json`
**Applied rules**: rule-ownership_verifier-internal_infra_override-74f17, rule-ownership_verifier-wildcard_stem_dns_override-a18c1

The Automattic engagement (2026-05-16) ran bucket-hunter Pass A against 20 brand stems (80 candidates, 26 hits) and a targeted a8c-prefix follow-up pass (51 candidates, 1 hit: a8c-jetpack-e2e-reports). Secret-hunter was invoked but crashed with an API 500 error after approximately one hour of runtime; the out/automattic/secrets/ directory is empty. This is the second time a long-running secret-hunter task has crashed mid-scan (previously on elastic). The ownership-verifier processed 9 buckets: 4 resolved to unowned via the existing bucket_aggregation_override rule (wordpress-backup, wordpress-prod, tumblr-backup, gravatar-uploads — all A=neg/B=neg/C=inconclusive), and 5 landed at unknown despite substantial evidence.

The 5 unknown verdicts fall into two structurally distinct failure modes. The first mode — and the more consequential one — is 'A=positive blocked by B/C structural impossibility.' Three buckets hit this wall: wpvip (612 GitHub hits in Automattic/wpvip-base and related repos, including a repo literally named after the product), wpcloud (379 hits across Automattic/wpcloud-station, Automattic/jetpack-wpcloud-sso, and Automattic/wpcloud-externals-example), and a8c-jetpack-e2e-reports (6 hits, all in Automattic/jetpack-e2e-reports — a dedicated repo whose sole purpose is Jetpack E2E reporting, with the bucket name hardcoded verbatim in bin/generate-report-s3.sh, bin/s3-client.js, and src/config.js). In all three cases B=negative is structural — these are internal CI/infrastructure buckets that are never referenced in archived web pages — and C=inconclusive is structural — all S3 buckets CNAME to generic AWS pools, and no program-controlled domain is expected to CNAME to an internal test-report bucket. The 2-of-3 positive-signal rule cannot be satisfied by any amount of additional investigation when the asset class is an internal bucket. The snapchat engagement produced the same structural failure on sc-core (A=neg/B=neg/C=positive) and sc-corp (A=ambig/B=neg/C=inconclusive), confirming the gap is program-agnostic.

The a8c-prefix discovery is a notable side-effect of the verifier work. 'a8c' is Automattic's internal engineering shorthand (A=first letter, 8=letter count between A and c, c=last letter of 'Automattic') and appears throughout their internal tooling as a bucket and repo prefix. The jetpack-prod verifier's investigation of Automattic/jetpack-e2e-reports surfaced this convention, which led to the targeted follow-up bucket-hunter pass. That pass found a8c-jetpack-e2e-reports (101,994 objects, auth-read-only) on the first try. This pattern — verifier work revealing a naming convention that drives a second hunter pass — is worth building into the workflow: when the verifier finds a literal bucket name reference in an org repo that uses an unexpected prefix, bucket-hunter should re-run with permutations of that prefix.

The second unknown failure mode is 'A=ambiguous because bucket name is a suffix-match on a longer org term.' jetpack-prod hit 139 GitHub results, but all were substring matches on 'jetpack-production' and 'jetpack-product' — zero references to the literal bucket name 'jetpack-prod.' woocommerce-backup hit 69 hits, all third-party WordPress plugin and backup-tool repos with zero Automattic org hits. Both are structurally indistinguishable from squatters. These are narrative observations only — no rules are proposed for them, because the cases are adequately handled by the existing unknown verdict floor combined with human review.

For future revisits of the automattic slug: (1) skip secret-hunter Pass A against the Automattic org until the API 500 crash is diagnosed — the org has 1,500+ public repos and the task runtime likely exceeds the API's connection window; run Pass B (noseyparker on a targeted clone list) instead. (2) If the internal_infra_override rule is applied, re-run the verifier on wpvip, wpcloud, and a8c-jetpack-e2e-reports — all three should promote to owned and become eligible for report drafting. (3) woocommerce-backup remains at unknown and is low-priority without additional A signal.

## 2026-05-16 — snapchat
**Proposal**: `memory/lessons/proposals/20260516-164056-snapchat.json`
**Applied rules**: rule-bucket_hunter-basename_skip-31083, rule-bucket_hunter-basename_skip-eb54c, rule-bucket_hunter-basename_skip-06e32

Snapchat (Snap Inc., bug_bounty tier, critical cap) was selected by the v2 OSINT-aligned scout rubric (score 8, has_source_code=true). The engagement ran all three secret-hunter passes and one bucket-hunter pass. Pass A trufflehog scanned all 56 Snapchat public repos in 10m35s — 0 verified secrets. Passes B and C ran noseyparker over 89,506 blobs (1.63 GiB) across 3 repos and found 0 matches. Ten S3 bucket candidates were checked for ownership; 6 resolved as unowned via the bucket_aggregation_override rule, 4 locked at unknown (bare-brand or internal-infra ambiguity). No reports were drafted.

The secrets outcome is a useful negative signal rather than a failure: Snap operates one of the largest-scale consumer applications on GCP (feelinsonice-hrd.appspot.com), not AWS, and their 56 public GitHub repos are engineering SDKs and reference implementations (camera-kit, dagger-browser, KeyDB). These repos are maintained by an org with a mature secrets-hygiene posture. Pass A returning zero hits on a 56-repo org with a 10m35s wall-clock cost suggests future revisits should skip Pass A entirely and focus budget on the private-ecosystem equivalent — if Snap ever has a leaked credential, it is more likely in an internal-facing project not visible on github.com/Snapchat.

The bucket scan surfaced a structural gap in the ownership-verifier's 2-of-3 rule. Two buckets — sc-core and sc-corp — are very likely Snap-owned based on out-of-band evidence: the sc-core.net and sc-corp.net DNS zones are on AWS Route53, registered via MarkMonitor (Snap's enterprise registrar), and both stems are explicit Tier A critical wildcards in the H1 program scope (*.sc-core.net, *.sc-corp.net). Snapchat's own public GitHub repos (KeyDB, dagger-browser, pixel-server-gateway) reference github.sc-corp.net as their internal GitHub Enterprise host. Despite all this, the verifier locked both at unknown because Check A (GitHub code search) and Check B (Wayback CDX) are both structurally blind to internal services: internal CI/CD infra does not appear in public code, and internal tooling URLs do not get crawled by Wayback. The 2-of-3 rule has no path to owned for internal-infra buckets even when DNS-zone control is provable. This is the most consequential finding of the engagement — not a leaked credential, but a logic gap that future revisits will need a human decision on.

The Wayback CDX transient timeout on the bare 'snapchat' bucket (gau returned 0 URLs; CDX API curl exit 28) blocked the bucket_aggregation_override from firing and kept the verdict at unknown instead of unowned. This is the same failure mode observed in the cloudflare engagement's backup-cloudflare bucket (gau returned 0 bytes). Two occurrences in two different engagements suggest a systematic reliability issue: when gau silently returns nothing, the verifier marks Check B inconclusive instead of negative, which prevents the override from firing and leaves the bucket at unknown instead of correctly promoting it to unowned. The fix is either a CDX retry on curl timeout or a distinct wayback_unreachable state that the override can treat like negative.

The override rule performed correctly on the remaining candidates: bitmoji (Snap-acquired Bitstrips brand, but bucket in us-east-2 with zero GH/Wayback footprint — unowned), playcanvas (Snap-acquired engine whose real S3 buckets are apps.playcanvas.com and static.playcanvas.com in eu-west-1; the bare 'playcanvas' bucket is in ap-southeast-1 — region and naming convention both diverge — unowned), spectacles (bare product-line name, zero evidence — unowned), sc-core-backup and sc-core-data (stem shares the sc-core.net zone but no DNS cross-link to the bucket; override fired cleanly — unowned). This is the fourth engagement (after indrive, 8x8, cloudflare) where the override has correctly prevented a false-positive report. Future revisit advice: if revisiting snapchat, bypass Pass A (56-repo org is clean), run Pass B and C on any newly public repos, and request a human pre-flight decision on sc-core and sc-corp before any bucket-related action.

## 2026-05-16 — elastic
**Proposal**: `memory/lessons/proposals/20260516-042355-elastic.json`
**Applied rules**: rule-bucket_hunter-basename_skip-ab4c5, rule-secret_hunter-passA_timeout_floor_secs-d3ea2

Elastic (HackerOne bug_bounty, $50–$15k, 57 in-scope assets). Ran secret-hunter trufflehog Pass A against the elastic GitHub org (~600 public repos), gh code search Pass B across four high-value token patterns, and bucket-hunter against 200 candidates across 8 brand stems. Pass A covered 250 of ~600 repos before the 10-minute timeout; that partial scan produced 1 verified-live SauceLabs credential in elastic/elasticsearch-js at commit bacd515545, file test/utils/keys.js, committed 2014-01-17 (~12-year exposure). The credential was confirmed valid at scan time by trufflehog's issuer-side check (Verified=true, VerificationFromCache=false). Report drafted and submitted to H1 as report #3739639, severity Low (capped by the 'elastic.co credentials' in-scope asset). Bucket-hunter found 64 existing buckets out of 200 candidates; ownership-verifier ran on 3 representative cases (elastic-github-org → owned, elastic-static → unowned, found → unknown).

Pass A on the elastic org is the engagement's strongest lesson. The mercadolibre and 8x8-bounty retros noted that mature orgs with >50 repos and good CI/CD hygiene tend toward low Pass-A yield. The elastic engagement is a direct counterexample: Elastic has ~600 repos, modern push-protection-style hygiene (Pass B showed all CI token references are env-var placeholders, not inline values), and yet a 12-year-old deleted test fixture slipped through. The age distribution matters: a credential committed in 2014 predates GitHub secret scanning, trufflehog push-protection, and most modern hygiene tooling. Older orgs with long git histories are a productive surface for Pass A precisely because the historical tail is long. For future engagements, the H3 narrative note should be read as 'mature-org hygiene applies to recent commits; the historical tail remains a viable surface.'

The 10-minute trufflehog timeout was the binding constraint. Pass A covered ~250/600 repos (~42% coverage) before timing out. At ~24 seconds per repo (observed rate from the engagement), full-org coverage requires ~4 hours. The second-pass background run (45-min cap) was cancelled by the user while still in the git-clone phase for elasticsearch and kibana — the two heaviest repos in the org. If those repos contain additional historical credentials, they remain unscanned. For future runs against large orgs (>200 enumerated repos), a minimum timeout floor should be enforced rather than relying on the agent's default cap.

The bucket-hunter produced two ownership outcomes worth noting. The 'elastic-static' bucket (687 objects, 4MB, FCKeditor content pre-2010) got a clean A=negative + B=negative + C=inconclusive verdict → unowned via the existing aggregation-override rule (rule-ownership_verifier-bucket_aggregation_override-1c25c from 8x8-bounty). The rule fired exactly as intended — no manual triage needed. The 'found' bucket produced the now-familiar common-word ambiguity: 'found' generates 10,832 prose hits inside org:elastic (it is one of the most common English words), wayback returned 34 phrase-collision hits ('not found', 'results found'), and found.elastic.co exists but CNAMEs to Fastly, not to this S3 bucket. The bucket was empty (0 objects), so even a hypothetical 'owned' verdict would yield nothing. This is the third engagement (after mercadolibre brand-stem and indrive bare-brand) where a structurally unresolvable asset name produces an unknown verdict — the pattern across engagements is consistent enough to justify a basename_skip entry for 'found'.

For the next visit to this slug: Pass A is still worth running, but requires a substantially larger timeout budget. The 250 repos scanned in pass 1 include many of the lighter client libraries and beats agents; the remaining ~350 include elasticsearch, kibana, logstash, and cloud services — the heaviest and most historically interesting repos. Recommend launching Pass A with a 3–4 hour cap and allowing it to run overnight. Pass B (gh code search) did not surface any actionable inline credentials and is consistent with the org's hygiene posture; it can be run first as a quick triage gate but should not substitute for Pass A. Bucket work is likely low-ROI on future elastic runs: the brand has a large third-party squatter footprint across all stems, and the aggregation-override rule will correctly suppress most 'found' and 'elastic-static' style false-positives.

The 81 repos surfaced by GH code search were almost entirely brand-name noise (bug-bounty aggregators, unrelated projects). If revisiting inDrive for secrets, the meaningful sources are not on GitHub at all; consider mobile APK static analysis or traffic interception paths instead. Pass A+B+C against the org is not worth repeating.
